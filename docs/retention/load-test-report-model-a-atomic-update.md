## 5. 분석

### 5-1. CPU는 병목이 아니다

Grafana 모니터링 기준 테스트 구간 중 CPU 사용률은 **약 6%**에 머물렀다. 서버는 20코어에 가상 스레드를 사용하므로 스레드 포화도 문제가 없다. CPU/스레드 레이어에서 병목이 발생하지 않았다.

### 5-2. HikariCP 커넥션 풀이 1차 병목이다

현재 `maximum-pool-size=8`이다. 400개 요청이 동시에 유입되면:

```
요청 400개 → HikariCP pool (size=8) → DB
               └─ 8개만 즉시 처리
               └─ 392개는 커넥션 대기 큐에서 블로킹
```

커넥션을 빨리 얻은 요청 ≈ min(98ms), 마지막으로 얻은 요청 ≈ max(614ms)로, 편차가 대기 시간의 차이다. CPU는 6%인데 레이턴시가 수백 ms인 이유가 바로 이 **I/O wait(커넥션 대기)**이다.

### 5-3. DB row-level lock은 2차 직렬화 요인이다

Atomic UPDATE는 `events` 행에 row-level exclusive lock을 걸고 직렬로 처리한다. 커넥션 풀을 늘려도 동일 행을 수정하는 UPDATE는 DB 레벨에서 직렬화가 이루어지므로 레이턴시를 완전히 제거할 수는 없다.

### 5-4. 정리

| 레이어 | 상태 | 비고 |
|--------|------|------|
| CPU | 여유 (6%) | 병목 아님 |
| 가상 스레드 | 여유 | 병목 아님 |
| HikariCP pool | **병목** | size=8, 대기 큐 392개 |
| DB row lock | 구조적 직렬화 | Atomic UPDATE 특성상 불가피 |
| 정합성 | **완전 보장** | 정원 초과 0건 |

## 6. 커넥션 풀 튜닝 실험 — pool=20 결과

### 6-1. 실험 조건

- `HIKARI_MAX_POOL_SIZE=20` 으로 재배포 후 동일 시나리오 실행
- 테스트 일시: 2026-06-02 22:15:01 KST
- 원시 데이터: `load-test/results/20260602_221500_raw.json`

### 6-2. pool=8 vs pool=20 비교

| 지표 | pool=8 (baseline) | pool=20 | 변화 |
|------|-------------------|---------|------|
| 테스트 지속 시간 | **1초** | 2초 | ▲ 2배 |
| 유효 처리량 (RPS) | **400 req/s** | 200 req/s | ▼ 50% |
| avg | **292ms** | 432ms | ▲ +140ms |
| p50 | **286ms** | 439ms | ▲ +153ms |
| p90 | **429ms** | 584ms | ▲ +155ms |
| p95 | **474ms** | 623ms | ▲ +149ms |
| p99 | **555ms** | 732ms | ▲ +177ms |
| max | **615ms** | 767ms | ▲ +152ms |
| 신청 성공 (200) | 100건 ✓ | 100건 ✓ | 정합성 유지 |

**pool을 늘렸더니 오히려 느려졌다.**

### 6-3. 원인 분석 — 핫 row 집중 현상

Atomic UPDATE는 `events` 테이블의 **단일 행**에 exclusive lock을 건다. pool size가 커질수록 동시에 같은 행에 UPDATE를 시도하는 커넥션 수가 늘어나 DB 내부 lock wait가 증가한다.

```
pool=8  → HikariCP가 앞단에서 직렬화 → DB에 8개씩 전달 → row lock 대기 짧음
pool=20 → DB에 20개씩 동시 도달 → 같은 행 lock 경합 심화 → 전체 wait 증가
```

pool=8일 때는 HikariCP 대기 큐가 사실상 **DB 부하를 완충하는 역할**을 했다.
pool=20은 그 완충이 줄어들면서 DB 레이어에서 병목이 더 심해졌다.

### 6-4. 초당 분포 비교

| 구간 | 처리 건수 | avg | p95 |
|------|-----------|-----|-----|
| pool=8, t=0 | 400건 (전부) | 293ms | 474ms |
| pool=20, t=0 | 81건 | 316ms | 466ms |
| pool=20, t=1 | 319건 | 462ms | 634ms |

pool=20에서 2초에 걸쳐 처리됐으며, 후반 요청의 대기가 누적돼 레이턴시가 더 높아졌다.

### 6-5. 결론

Atomic UPDATE(단일 핫 row) 패턴에서는 **커넥션 풀 증가가 성능을 개선하지 않는다.** DB row lock 직렬화가 근본 병목이며, 이 전략의 처리량 상한은 구조적으로 정해져 있다.

> **현재 서비스 규모(정원 100~150명, 경쟁 400명)에서 pool=8, p95 474ms는 허용 가능한 수준이다.**
